1 Executive Summary TLP:GREEN

GPT-Proxy Backdoor is a financially motivated supply-chain attack campaign targeting software developers and MLOps engineers who integrate large language model (LLM) APIs into their work. The campaign distributes malicious packages through two of the most trusted software distribution channels in the Python and JavaScript ecosystems — the npm and PyPI package registries — under names designed to blend into Kubernetes-adjacent tooling: kube-node-health (npm) and kube-health (PyPI). Both packages carry compiled native extensions that execute silently on installation, making them particularly dangerous in automated dependency-resolution workflows and CI/CD pipelines.

Once installed, each package drops an encrypted shell script to /tmp/.ns using XOR obfuscation with the key n4k8x2m6, then downloads and executes a second-stage Go binary from a GitHub repository controlled by the threat actor. This binary — identified as a modified chisel reverse tunnel client — establishes a persistent WebSocket tunnel over TLS port 443 to a Cloudflare-proxied command-and-control domain (sync.geeker.indevs.in). At the time of this analysis, the tunnel was fully functional: dynamic testing captured 121 MB of C2 traffic in under eight minutes, showing 20 parallel WebSocket connections initiating within two seconds of activation.

What distinguishes this campaign from commodity infostealers is the stage-2 payload's LLM API man-in-the-middle capability. The Go binary contains a proxy.GPTProxy struct and a proxy.toolCallState engine that position the implant as a transparent relay between the victim's LLM API calls and the upstream provider. The binary's string table references more than 40 LLM models across Anthropic, OpenAI, Google, Mistral, xAI, DeepSeek, and several Chinese reseller backends. The attacker's monetisation model is assessed with medium-high confidence to involve re-selling stolen API credentials through Chinese reseller platforms, consistent with the -xmind, -cloudsway, and -shubiaobiao provider suffixes in the routing table and with the actor's broader GitHub presence as an operator of Chinese GFW-circumvention proxy infrastructure.

The threat actor operates under the GitHub alias gibunxi4201, an account created in June 2025 that also maintains 53 Streamlit-deployed ArgoSB proxy nodes for Chinese internet users. Within 24 hours of public research disclosure, the actor deleted the kube-node-diag GitHub repository used to distribute the stage-2 payload — a rapid infrastructure-cleanup response indicating active monitoring of security researcher activity. The C2 domain remains live as of publication.

Severity assessment: Critical. The campaign's combination of supply-chain delivery, zero AV coverage, persistent encrypted tunnel, and API credential harvesting represents a high-severity threat to any organisation whose developers use npm or PyPI in conjunction with commercial LLM API access. Organisations with affected packages installed should treat all LLM API keys on the affected systems as compromised and rotate them immediately, regardless of whether the stage-2 payload was successfully activated.

3 Campaign Overview

Discovery. The campaign was first publicly documented by Aikido Security on 2026-04-22 in a blog post identifying the npm package kube-node-health and PyPI package kube-health as malicious. Both packages had been available on their respective registries and were removed following disclosure. This analysis began on the same day, building on that initial disclosure with independent sample acquisition, full static and dynamic analysis, infrastructure enumeration, and threat hunting.

Scope. Four unique ELF 64-bit samples are associated with this campaign. Two are first-stage droppers (one per distribution channel), and two are variants of the same Go stage-2 payload — one with full symbol tables (S4) and one compiled with the garble obfuscator (S3). S3 and S4 represent updated versions not present in the original Aikido blog analysis, indicating the actor pushed new builds after the initial research disclosure.

Targeting. The attack is broadly targeted at any developer or build system that installs dependencies from npm or PyPI without hash pinning. However, the LLM API routing table in S4 indicates a specific secondary interest in victims with access to commercial LLM API credentials. The package names (kube-node-health, kube-health) suggest the actor is specifically targeting Kubernetes-adjacent developer environments — the audience most likely to have both automated dependency pipelines and access to cloud AI APIs.

Impact model. The attacker gains two primary capabilities upon successful compromise: (1) a persistent reverse shell tunnel through which arbitrary commands can be run on the victim host, and (2) silent interception of all outbound LLM API traffic, including API keys and the content of requests and responses. The tool-call injection capability additionally allows the attacker to silently alter the behavior of AI agents running on the victim system — a novel impact class not seen in prior supply-chain malware campaigns reviewed by this analyst.

Infrastructure status at time of publication. The stage-2 distribution repository (gibunxi4201/kube-node-diag) has been deleted, breaking the dropper download chain for new victims. The C2 domain sync.geeker.indevs.in remains active. Systems already running the stage-2 binary are unaffected by the repository deletion and continue to beacon to the C2.

Scope note on S3 vs S4 S3 (garble-obfuscated) and S4 (full symbols) appear to be functionally equivalent payloads compiled from the same source at different obfuscation settings. S4 is analysed in depth as the primary sample due to its recoverable symbol table. S3 observations are noted where they differ.

6 Technical Analysis
📦
6.1 Initial Access — Supply Chain Compromise
T1195.001

The campaign delivers both dropper samples through legitimate software package registries, exploiting the implicit trust developers place in registry-hosted packages. The package names were chosen to blend into Kubernetes tooling ecosystems — environments where developers frequently install health-check, monitoring, and utility packages without detailed code review. Both packages carry compiled native extensions that bypass Python/Node source-code inspection entirely.

npm vector: The package kube-node-health includes a native Node.js addon (addon.node) compiled as a NAPI C++ shared object. Node.js automatically loads NAPI addons when the containing package is require()d, providing code execution without any further user action beyond npm install. The package.json main field points to a JS wrapper that triggers the require on import, meaning any downstream package that lists kube-node-health as a dependency causes execution.

PyPI vector: The package kube-health ships a pre-compiled CPython 3.11 Cython extension (kube_health.cpython-311-x86_64-linux-gnu.so). Cython extensions run as native code on import kube_health, similarly bypassing source-level analysis. Any pip install kube-health followed by an import in user code triggers the payload.

⚙️
6.2 Execution — NAPI Init, Fork, XOR Decrypt, Dropper Script
T1059.004

The S2 NAPI addon's entry point napi_register_module_v1 is called by the Node.js runtime when the module loads. The function's first action is to call fork(), immediately detaching execution from the Node.js event loop. The parent process returns a normal (empty) napi_value — the module appears to do nothing. The child process calls setsid() to detach from the controlling terminal and session, then proceeds with the payload.

napi_register_module_v1(env, exports): ; called by Node.js runtime on require() pid = fork() if pid != 0: return napi_value ; parent: return empty module — appears harmless ; child process continues: setsid() ; detach from terminal/session blob = read_embedded_data(offset=0x3a80, len=874) key = "n4k8x2m6" ; 8-byte XOR key xor_decrypt(blob, key) ; rolling XOR, key repeats cfg = getenv("KH_CFG") inject_cfg_into_script(blob, cfg) ; strstr(blob, "echo '") → replace placeholder fd = fwrite("/tmp/.ns", blob) chmod("/tmp/.ns", 0755) execl("/bin/sh", "/bin/sh", "/tmp/.ns", NULL)

Critical activation detail — stdin pipe, not environment variable. Initial dynamic analysis produced no output because the binary exits immediately without a valid KH_CFG value. Disassembly revealed that KH_CFG is read from the environment only as a passthrough — the decrypted script does not use an env-var-based delivery mechanism at runtime. Instead, the dropper script itself pipes a hardcoded base64 blob to the stage-2 binary via stdin: echo 'BASE64...' | /tmp/.kh &. This design defeats most sandbox emulators, which test environment-variable-based configuration gates but rarely inject stdin payloads during automated analysis.

6.3 Defense Evasion — Four Layers
T1027 T1140 T1036.005 T1562.001

Layer 1 — XOR obfuscation of dropper script (S2). The 874-byte embedded blob is XOR-encrypted with the repeating 8-byte key n4k8x2m6. This removes all readable strings (shebang, URLs, shell commands) from the dropper binary, preventing signature matching on the blob content. The key is itself stored as a plain string in the binary, meaning it is recoverable by static analysis, but the obfuscation is sufficient to defeat most automated string-based scanners.

Layer 2 — garble obfuscation of stage-2 (S3). The garble-compiled variant randomises all Go package, type, and function names at compile time. Package names become random strings like _RndZzhTd, oor2y7Hoz9, wIXGgavYUm. The chisel proxy struct references, LLM model names, and C2 URL strings are not present as readable symbols. Only JSON struct field tags — which garble cannot safely randomise without breaking JSON serialisation — survive: json:"socks,omitempty", json:"tunnels", json:"proxy,omitempty".

Layer 3 — TLS verification disabled (stage-2). The chisel client is launched with --tls-skip-verify, confirmed by the log string "client: TLS verification disabled" observed during dynamic analysis. This means the attacker's Cloudflare-fronted backend does not need a valid certificate chain, and any TLS anomaly inspection at the network perimeter will not trigger on certificate issues.

Layer 4 — hidden files and fake module path. All filesystem artefacts use a dot-prefix under /tmp/ (.ns, .kh, .nhc.enc). The stage-2 binary embeds the fake Go module path github.com/kubernetes/node-health-check as its declared import path, which appears in go version -m output and process listings, making casual inspection read it as a legitimate Kubernetes tool.

🔑
6.4 Credential Access — LLM API Key Interception
T1557

The primary credential-access mechanism is a transparent LLM API proxy implemented in the stage-2 binary. The proxy.GPTProxy struct intercepts outbound HTTP/S requests destined for LLM provider API endpoints. When a victim application makes an LLM API call (e.g., POST /v1/chat/completions with Authorization: Bearer sk-...), the proxy relays the request to the C2 and simultaneously forwards it upstream to the actual provider, returning a normal response to the victim. The victim's application sees no difference in behaviour.

The proxy.toolCallState and proxy.rFuncCallState structures extend this capability to the tool-call layer: the proxy can inspect, log, and modify the tool_calls array in LLM responses before they reach the victim application. In a real-world agentic workflow (e.g., an AI agent that uses tools to query databases, send emails, or modify code), this means the attacker can silently redirect tool invocations or inject additional tool calls — an impact class beyond simple credential theft.

📡
6.5 Command & Control — chisel WSS Tunnel via Cloudflare
T1072 T1071.001

The stage-2 binary incorporates chisel, an open-source HTTP/WebSocket tunnelling tool. The client connects to wss://sync.geeker.indevs.in:443 with TLS verification disabled, establishing a multiplexed reverse tunnel over a single WebSocket connection. The chisel server on the C2 side can use this tunnel to open reverse TCP connections back into the victim network on any port. The 100 ms reconnect interval ("Retrying in 100ms") ensures near-instant recovery from connection interruption.

The C2 domain sits behind Cloudflare's reverse proxy, which provides the attacker with DDoS protection, hides the real backend IP, and supplies a legitimate Cloudflare TLS certificate — eliminating the certificate anomaly signal typically associated with C2 infrastructure. The domain itself was registered for free via Stackryze Domains, leaving no payment trail.

ngrok fallback. S4 contains the string pairconnect.ngrok-agent.com, which is the ngrok agent pairing infrastructure endpoint. If the primary chisel C2 is unavailable, the binary can establish a fallback ngrok reverse tunnel. The specific ngrok URL is dynamically assigned and not present in the binary.

💥
6.6 Impact — API Abuse and Agentic Workflow Hijacking
T1657

Assessed primary impact is ongoing LLM API credential abuse: stolen API keys are used to make API calls through Chinese reseller backends, generating costs billed to the victim while the attacker profits from resale. The volume of stolen keys aggregated across all campaign victims is unknown but potentially significant given the campaign's supply-chain delivery mechanism.

Secondary impact is persistent shell access to all victim hosts running S4. The chisel tunnel provides full TCP reverse-shell capability, enabling data exfiltration, lateral movement, ransomware deployment, or cryptomining on compromised developer workstations and CI/CD systems — all of which have elevated access to source code, secrets, and cloud credentials.

Tertiary impact — assessed MEDIUM confidence — is tool-call injection in agentic AI workflows. Any victim running AI agents that use tool calls (function calling in OpenAI/Anthropic APIs) while S4 is active may have had those tool invocations observed or modified. The potential for agent session hijacking in production AI pipelines is a novel and underappreciated impact surface.

No DNS queries for any other domain were observed during the 8-minute capture, including no queries for ngrok infrastructure — confirming the ngrok fallback path was not triggered.

TLS/WebSocket phase. Twenty or more parallel TCP connections were established to port 443 within two seconds of activation. Each connection sent a TLS ClientHello with SNI sync.geeker.indevs.in. INetSim presented a self-signed certificate; the client accepted it without validation (TLS verify disabled). The HTTP layer showed WebSocket upgrade requests (GET / with Upgrade: websocket headers) consistent with chisel's multiplexing protocol.

Reconnect behaviour. When INetSim dropped connections, the client reconnected within 100 ms, consistent with the hard-coded "Retrying in 100ms" string. The binary maintained a stable pool of 20 parallel connections throughout the capture, suggesting a configured parallelism setting in the embedded KH_CFG blob.

No exfiltration observed. Because INetSim returned synthetic responses rather than valid chisel server handshake data, the tunnel never fully negotiated and no application-layer payload (API keys, shell commands) was transmitted in recoverable form. A real C2 server would have completed the handshake and the implant would have become fully operational.

9 C2 Protocol Analysis

The C2 protocol is based on chisel (github.com/jpillora/chisel), an open-source HTTP/WebSocket tunnelling tool written in Go. chisel multiplexes multiple TCP streams over a single WebSocket connection using the yamux session multiplexer. The attacker has embedded the chisel client library directly into the stage-2 binary rather than deploying chisel as a standalone tool, making the binary fully self-contained.

10 LLM API Interception Capability

The stage-2 binary implements a full LLM API proxy layer in the Go proxy package. Three key structs are recoverable from S4's symbol table:

  • proxy.GPTProxy — the main proxy struct, holds upstream provider configuration, routing table, and the active connection pool to the C2
  • proxy.toolCallState — tracks in-flight tool calls per request, enabling per-call inspection and modification of tool_calls arrays in LLM responses
  • proxy.rFuncCallState — reverse function call state, used to inject attacker-specified tool invocations into ongoing conversations

The routing table in the embedded KH_CFG configuration maps each intercepted model name to a backend relay. The Chinese reseller suffixes (-xmind, -cloudsway, -shubiaobiao) suggest the stolen credentials are re-billed through Chinese reseller APIs rather than directly against the upstream providers, potentially avoiding per-key rate limits and providing an additional layer of obfuscation for the attacker's billing trail.

13. Detection Signatures

Six YARA rules, three Sigma rules, and six Suricata rules were developed from this analysis. The rationale for each rule is described below — understanding the detection logic enables analysts to tune thresholds and anticipate evasion by future variants. All rules are TLP:GREEN and may be shared freely.

Detection rationale: YARA rules target three layers of the campaign: (1) the XOR key and blob size unique to the S2 NAPI dropper, (2) the garble-obfuscated Go binary using surviving JSON struct tag strings, and (3) the activated chisel RAT using WebSocket C2 domain and Go runtime markers. Rules 5–6 provide generic coverage for the dropper shell script pattern and the stdin pipe activation mechanism in process memory.

15. Recommendations

Recommendations are tiered by urgency and implementation horizon. Immediate actions address active exposure from the known campaign IOCs. Short-term actions harden the supply-chain attack surface. Strategic actions address the root-cause architecture gaps that made this campaign possible.

Immediate 0 – 72 hours
Block C2 domain at DNS resolver and HTTP proxy
Add sync.geeker.indevs.in and pairconnect.ngrok-agent.com to DNS block lists and proxy deny lists. Do not rely solely on IP-based blocking — Cloudflare IPs are shared infrastructure. DNS blocking provides earlier detection (query logged before connection) and works regardless of port.
Hunt for campaign IOCs on all Linux hosts
Grep process lists, open file handles, and filesystem for: /tmp/.ns, /tmp/.kh, /tmp/.nhc.enc, /tmp/.nhc-switch. Check npm list -g kube-node-health and pip show kube-health on all developer workstations and CI/CD build agents. Query SIEM/EDR for the hash list from Section 12.
Audit npm and PyPI packages installed in CI/CD and developer environments
Generate a bill of materials for all packages currently installed. Cross-reference against the IOC package names. Check for any preinstall, postinstall, or install scripts that write to /tmp/ or execute downloaded binaries.
Submit abuse reports to Stackryze Domains and Cloudflare
Report sync.geeker.indevs.in to Stackryze Domains (indevs.in abuse contact) for C2 hosting abuse. Submit to Cloudflare abuse portal with campaign reference. These are low-friction actions likely to disrupt the infrastructure for any victim still reaching out.
Short-term 1 – 4 weeks
Implement pre-install script scanning in CI/CD pipelines
Configure npm and pip to block packages with native C/C++ extensions or preinstall/postinstall scripts without an explicit allow-list approval. Tools: socket.dev (npm), pip-audit, osv-scanner. In CI, run npm ci --ignore-scripts for all non-explicitly-approved packages. This would have blocked S2 at install time.
Deploy file-creation detection rules for /tmp hidden executables
Enable auditd rules or EDR telemetry to alert on: (a) executable files created in /tmp/ with dot-prefixed names, (b) execve calls on paths matching /tmp/.*, (c) chmod +x applied to /tmp/ paths. The Sigma rules in Section 13 provide ready-made detection logic for Linux auditd and sysmon-for-linux.
Enrich MISP events and share with sector peers
MISP Event 1097 (sunrise) and Event 4 (agentic) contain the full IOC set. Share via MISP synchronisation with relevant sector ISACs. The campaign targets developer environments broadly — any organisation using LLM APIs in automated pipelines is a potential target. TLP:GREEN permits unrestricted sharing.
Monitor VT for new detections on S1 and S2 droppers
Set VirusTotal Intelligence alerts on the S1 and S2 hashes. As AV vendors develop behavioural signatures for the dropper pattern, detection rates will rise. First detection on S1/S2 is expected within 2–4 weeks based on historical supply-chain dropper detection lag patterns.
Strategic 1 – 6 months
Implement LLM API key rotation and per-session scoping
The campaign's primary objective is API key theft for LLM resale. Short-lived, per-session tokens with minimal scope (read-only where possible) limit the blast radius of a key compromise. Implement token rotation on a 24-hour cycle for automated workloads. Audit all locations where LLM API keys are stored in plaintext (environment variables, config files, CI/CD secrets).
Establish a private package registry with verified mirror
Mirror approved npm/PyPI packages in a private Nexus/Artifactory instance. Require all production and CI builds to install from the mirror only. This eliminates the typosquat/supply-chain attack vector entirely for packages not in the approved list, while maintaining a full audit trail of which packages are in use.
Develop YARA scanning capability for package ecosystem files
Integrate YARA rule scanning into the package ingestion pipeline for the private registry. Scan all .so, .node, and compiled extension files against the GPT_Proxy_Backdoor rule set and the broader supply-chain malware YARA corpus (e.g., Elastic's open-source YARA repo). Automated scanning at ingestion catches campaigns before they reach developer machines.
Threat model LLM API usage in automated pipelines
Conduct a STRIDE or PASTA threat model of all systems where LLM APIs are called automatically (CI/CD, agents, code assistants). Map trust boundaries around API key storage and transmission. The GPT-Proxy Backdoor campaign specifically targets these pipelines — they represent a novel and undermodeled attack surface as LLM adoption accelerates.
